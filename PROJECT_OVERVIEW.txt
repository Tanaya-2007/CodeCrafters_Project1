
SarkariTrack — Competitive Exam & Recruitment Dashboard (PS-1)
Team project overview — plain-English guide for all members

1. WHAT IS THIS PROJECT?
------------------------
Candidates for government exams (UPSC, SSC, Railways, Banking, State
PSC, Postal, Defence) must check many official portals daily for
notifications, deadlines, exam dates, syllabus changes and admit cards.
Information is scattered, so people miss deadlines.

SarkariTrack is ONE centralized dashboard that:
  - collects updates from official government portals automatically,
  - converts them into clean, validated records,
  - lets each user track their own applications with countdowns,
  - sends deadline / update alerts,
  - keeps an admin in control of what goes public.

Problem Statement: PS-1, Competitive Exam & Recruitment.


2. TECH STACK (do not change without team agreement)
---------------------------------------------------
  Frontend : HTML + CSS + vanilla JavaScript (no frameworks)
  Backend  : Node.js + Express (REST JSON API, serves the frontend too)
  Database : PostgreSQL (teammate-owned, see database/schema.sql)
  Scheduler: node-cron inside the backend (checks portals every 6 hours)
  Parsing  : cheerio (server-side HTML parsing of official pages)


3. HOW THE SYSTEM WORKS (end to end)
------------------------------------
  1. SCHEDULER wakes up (every 6 hours, at server start, or when an
     admin presses "Run check now").
  2. SCRAPER fetches each official portal (polite: browser user-agent,
     15-second timeout, one portal at a time, 1-second gap, max 25
     notices per portal, one retry on failure).
  3. VALIDATION runs on every notice:
       - organisation + title + official URL must exist (else discarded),
       - end date must not precede start date (bad date dropped),
       - SHA-256 fingerprint decides duplicate vs changed.
  4. MODERATION (admin verification — nothing auto-publishes):
       - fresh notices enter as New (hidden from candidates),
       - ambiguous notices enter as Needs Review,
       - admin Approves -> Verified (public) or Rejects (hidden forever),
       - "Approve all New" publishes a backlog in one click (logged).
  5. CHANGE DETECTION: re-scraped notices are compared field-by-field
     with the stored copy. Changed fields -> status Updated + a row in
     the update history. Identical -> only the last-checked time moves.
  6. DASHBOARD shows Verified/Updated records only, with live
     countdowns computed from deadlines.
  7. USER TRACKS an exam -> status pipeline:
     Interested -> Applied -> Admit Card -> Exam Done -> Completed
     (server-enforced: forward one step only, repeats idempotent,
     backward/jump attempts rejected, Completed never wraps around).
  8. ALERTS: in-app notifications at 7 days + 1 day before deadlines
     plus official-update alerts, per the user's preferences.
  9. PERSONALIZATION: profile captures qualification, stream, state,
     age + interests (frontend/js/recommend.js). Engine verdicts every
     exam family as Eligible / One-step-away / Later with reasons;
     For-You page links live notices in; every exam-details page shows
     the exact books + subjects + official links to clear that exam.
  9. FAILURE RULE: a portal failing only writes a job log
     (Source Unavailable). Trusted stored data is NEVER deleted.

6. DATABASE (PostgreSQL — teammate's ownership)
----------------------------------------------
  Canonical definition: database/schema.sql (8 tables + 1 view + seeds).
  - users .............. login + alert_pref_days {7,1}
  - official_sources ... the 8 portals + last status/check/items
  - exams .............. notices; dates NULLABLE (listings rarely carry
                         windows); dedup UNIQUE(org, title, url)
  - exam_updates ....... JSONB field diffs + snapshots (history pages)
  - applications ....... server-owned tracker (user, exam, status)
  - alerts ............. idempotent alerts (unique per user/exam/type/date)
  - scrape_jobs ........ scheduler audit per portal per run
  - tokens ............. login sessions (backend only, not shown in UI)
  - v_exams_public ..... Verified/Updated only (what candidates see)
  Backend auto-creates these IF NOT EXISTS when DATABASE_URL is set.
  Without Postgres it runs on ephemeral memory: 100% live data, but
  everything is forgotten on restart (fine for UI demo, not evaluation).


7. HOW TO RUN
-------------
  Full live mode (real data):
    cd backend
    npm install        (once only)
    node server.js     (serves site + API at http://localhost:3000)
    First boot needs ~2 minutes (all portals scraped once).
    Candidate: register. Admin: admin@sarkari.track / admin123
    (override with backend/.env — copy .env.example first).
    Admin first step: Review -> Approve all New (fills the dashboard).
  UI-only preview (mock data, design checks only):
    Open frontend/*.html with VS Code Live Server.
    Banner reads "Demo data" — backend must run for real data.
  With teammate's Postgres:
    Put DATABASE_URL=postgres://... in backend/.env and restart.
    No code changes needed anywhere.


8. KEY RULES WE FOLLOW (from the PS, all implemented + tested)
--------------------------------------------------------------
  - Official site is the truth; we store its URL + retrieval time.
  - Required fields present; end >= start; duplicates never duplicate.
  - Ambiguous extraction -> Needs Review, never auto-published.
  - Source failure never erases trusted data.
  - Alerts idempotent (same deadline alerts once).
  - No dummy data in live mode; no API rate limiting (functionality first).
  - Tracker transitions are server-validated; Completed is terminal.
